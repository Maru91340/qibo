# 奇波小助手 UI/UX 复评与首页优化方案

评估日期：2026-11-07。对象：`D:/qibo/qbxzs`，重点是首页，并覆盖从首页进入角色、奇波图鉴的连续体验。参考：[蓝色星原：旅谣 BWIKI 首页](https://wiki.biligame.com/ap/)。

**结论：当前界面具备基础的卡片和配色规范，但还没有形成合格的游戏资料首页。主要问题是内容优先级错误、图片用途不匹配、资料可信度表达混乱，以及小程序端的筛选布局缺陷。继续加渐变、圆角、背景图和功能入口，收益很小。应先修正真实内容与页面结构，再统一视觉。**

本次仅新增本文档，不修改业务代码、旧报告或图片数据。文中的方案、尺寸、预算和测试目标均为待实施要求，不表示已经完成。

## 2. 参考网页真正值得借鉴什么

参考站的优势不是黑色边框或大面积背景，而是**把玩家认识的角色、奇波直接变成可点的内容**。当前小程序主要展示“有什么功能”，网页更直接展示“有什么游戏对象”。

| 观察点 | 参考网页的有效做法 | 小程序应如何转换 |
| --- | --- | --- |
| 游戏辨识 | 首屏有明确的公测主视觉；角色和奇波拥有可识别图片 | 保留一个主视觉焦点；首页展示少量具体角色和奇波，图片直接进详情 |
| 图片语义 | 角色使用人物头像，奇波使用对应图标 | 每个图片位指定用途和对象，不用随机灵子卡图代表所有功能 |
| 浏览效率 | 连续图片矩阵，名字贴近图片，分类标题带“查看更多” | 移动端每类先展示 4 个对象，名称固定可见，分类页承接完整内容 |
| 分类边界 | 角色、奇波、灵子、物品分区明确 | 首页以“角色速查”“奇波速查”分区，避免几十张同形功能卡纵向堆叠 |
| 时效内容 | 公测日期和兑换码有明确语境 | 首页只保留当前有效事件；时间、来源和有效状态放到相关内容中 |
| 全量入口 | 侧栏承担目录职责 | 用“全部图鉴/全部工具”承接低频目录，不把桌面侧栏整体塞进首页 |

不建议照搬：桌面八列密集图块、厚黑描边、所有条目平铺、右侧悬浮工具条、大幅淡背景和长侧栏。手机上的可触面积、短视线和滚动成本不同。

参考站本身也有密度过高、角标拥挤、长页滚动等问题；它是内容组织与素材使用的参照，不是全部视觉细节的标准答案。

## 3. 首页专项问题与具体改法

### H01 / P1：首屏在介绍平台，未尽快给出查询入口和具体内容

**现象：** S2 的顺序是轮播 → 倒计时 → 统计 → 两页快捷宫格 → 搜索 → 版本信息。具体角色、奇波内容没有出现在这一屏。轮播中的“立即查看”也缺乏明确任务指向。

**原因：** 首页把运营、规模证明、导航和查询串行堆叠，所有模块都先于实际资料。对于已经在游戏中的回访者，每次都要越过宣传层。

**改法：** 搜索置顶；保留一个 140–150px 高的主视觉；日期与事件状态并入主视觉；下方固定快捷入口，然后直接展示角色和奇波。将长版本信息和低频目录后移。保留“图鉴预览”和“类型导航”两种入口是合理的：前者直达对象，后者进入分类，不应再重复一整组大型功能卡。

**验收：** 390×844 目标屏幕中，不滚动即可使用搜索、进入角色/奇波分类并看到至少一排可识别的真实对象；320px 宽度不出现横向整页溢出。

### H02 / P0：图片分配方式错误，导致即使出图也未必好看

**证据：** `index.vue` 的 `loadMeta()` 从灵子 `icon` 收集图片，再用 `hashIndex()` 分配给轮播和所有功能卡。分配是确定性的哈希映射，但与内容语义没有明确对应；资料集合变化后也可能换图。

**后果：** 队伍、材料、地图等入口可能使用无关灵子插画；120px 级缩略图被放进 360rpx 宽的装饰区域，存在放大模糊风险；低透明度和多层渐变进一步削弱主体。S2 中几乎看不到游戏人物，也不能仅凭该截图区分是缺图、遮罩过重还是旧数据。

**改法：** 首页改为明确的图片清单：主视觉一个横图；角色使用专用头像；奇波使用专用图标；攻略封面按文章选；工具采用统一图标。每个用途有独立裁切、安全区和失败回退。图片选型见第 5 节。

**验收：** 不再按哈希给业务入口配图；图片与名称逐一核对；首页没有将整张攻略图、低分辨率卡牌或随机壁纸当头像/横幅的情况。

### H03 / P1：轮播承担了不适合轮播的职责

**证据：** 当前轮播自动每 5 秒切换；“公测定档前瞻”跳转福利码，“奇波营地大作战”跳转泛玩法指南。按钮统一叫“立即查看”。

**问题：** 信息会在用户阅读时更换；画面标题没有清楚说明目标页；入口点开后可能找不到刚才承诺的内容。

**推荐：** 默认一个静态主视觉。只有确有两个仍有效、内容不同的活动时才保留手动轮播，并显示“1/2”；核心搜索和图鉴入口永远在轮播外。按钮改成“查看公测信息”“查看家园玩法”等目标明确的文案。公测信息必须有对应的完整内容承接，不能继续泛指到福利码。

**验收：** 不靠等待轮播找到重要入口；每张图的标题、按钮、落地内容一致；不把自动滚动次数当互动效果。

### H04 / P1：四项统计占用首屏，而且口径容易误导

**证据：** 当前首页“官方图”的计算只是若干分类里有 `icon` 的条目数量，排除了角色、奇波和壁纸；不能证明图片的来源、权利状态或是否加载成功。“图鉴条目”累加多个有交集的目录，物品与材料等会重合。

**额外问题：** `stat` 的 `computed` 直接读取存储函数，没有明显的 Vue 响应式依赖；资料更新事件只执行 `loadMeta()`，不能保证已缓存的统计同步重算。截图和磁盘值已经不同，但未做运行缓存追踪，不能把差异全部归因于此。

**改法：** 删除首屏四格规模条。分类标题可显示该分类真实数量，更新时间与来源放列表页说明。必须展示总数时，先定义是否去重、是否包含示例和内置/云端范围；“官方图”这个字段建议取消。

**验收：** 示例不进入正式数量；同一实体不会被用来宣传多个总数；更新资料后数量同步；没有无解释的“—”。

### H05 / P1：快捷宫格与下方大目录重复，第二页隐藏低频入口

**证据：** 现有快捷区为两页×六格，搜索入口又与下方搜索框、分组目录重复；全部功能继续在下方大卡片中出现。分页指示色为金色，主轮播指示为蓝色。

**改法：** 使用固定 4×2 八入口：奇波、角色、灵子、物品、装备、元素克制、队伍编成、全部工具。搜索由顶部搜索框承担。地图是否进入八入口，取决于它是否能完成真实找点任务；不能因“有地图页面”就自动升为核心入口。若地图已具备有效体验，可与低频入口替换，并通过任务测试确认。

**验收：** 关键类型不必横滑发现；“全部工具”进入紧凑目录；首屏不同时出现分页宫格和一整套重复的大功能卡。

### H06 / P1：边距层级不统一，造成多个“套在里面”的白盒子

**证据：** `.page` 已设置左右 24rpx，倒计时、版本信息又有左右 24rpx 外边距；统计、快捷区、搜索与它们不在同一条竖线上。

**改法：** 全页统一一个外边距，建议以 390px 屏幕左右 16px 为设计基准。模块内部再用 12–16px 内边距。公告可以是薄条，不必每块都做有阴影的白卡。

**验收：** 搜索、主视觉、快捷区、分区标题和预览内容左右对齐；区别模块层级靠留白与标题，不靠不断向内缩进。

### H07 / P1：蓝、金、橙、红、绿都在争夺强调权

**现象：** 导航和统计为蓝色，快捷分页为金色，版本标题和倒计时为橙色，信息标签再混用多色；大多数卡片都有圆角和阴影。

**改法：** 行为只用一个主蓝色；日期、稀有度或奖励可以少量用暖色；错误、成功才使用对应状态色。普通分区标题用正文主色，取消“『版本信息』”的装饰括号。保留原生微信导航结构，先完成内容层级，再决定是否需要定制导航。

**验收：** 一屏只有一个主要视觉焦点；普通资料不和活动按钮同等抢眼；静态内容卡默认没有明显浮起阴影。

### H08 / P1：字号偏小、次要文字过浅

**证据：** 统计标签 21rpx、多个摘要 23rpx、快捷名称 24rpx，390px 宽时约为 10.9px、12px、12.5px。当前 `#97a0b5` 与白色的计算对比度约 2.62:1，与 `#f3f5fb` 约 2.40:1；橙色 `#d9841f` 与白色约 2.89:1。

**改法：** 常规正文建议 14px 起，说明文字建议 12px 起；次要内容减少字数，而不是继续变浅。以普通文本对比度至少 4.5:1、关键非文本控件至少 3:1 作为设计检查目标。`#5a6480` 对白约 5.88:1，可作为现有可复用的次要文字色之一。

**验收：** 浅色、深色分别检查实际文字和底色；日期、名称、筛选条件不依赖低对比度颜色；不同字号下检查截断，而非简单整体放大。

### H09 / P0：版本区混入不同时间、不同性质的信息

**证据：** 已展示“公测定档 11.26”，又把“2026 年起陆续”“全球预计 2026 末–2027”放在同一块；元素克制和组队教程也被归到“版本信息”。

**问题：** 用户无法判断哪项是当前公告，哪项是历史预测，哪项是玩法说明。本文不重新裁定全部游戏事实，但当前分类和时间表达已经存在明确的信息设计问题。

**改法：** 首页仅保留一条当前确认的公测事件；历史预测移到注明日期和来源的资料页。玩法内容归“新手必看”，每条一行标题加必要说明，先展示两条并提供“查看全部”。

**验收：** 公测、测试、海外安排分别注明范围和出处；没有把不同时期预测并列当最新情报；每条可点信息都能落到匹配内容。

### H10 / P0：首页承诺了尚不成立的提醒能力

**证据：** 首页展示“订阅提醒”；订阅页 `SUBSCRIBE_TEMPLATE_IDS` 为空，目前主要保存本机偏好。倒计时依赖无响应式时间源的 `computed`，跨天停留可能不更新；到期仅钳制为 0。

**改法：** 模板和服务端推送未完成前，把主视觉操作改为“查看公测信息”，不以“提醒我”作为主要承诺。公测事件设开始前、当天、开始后三种状态；进入首页或回到前台时重新计算，活动变更由内容配置更新。

**验收：** 未接入时不会提示“已订阅成功/届时通知”；跨日期、公测当天、公测后不出现永久“倒计时 0 天”；不为验证而真的订阅用户消息。

### H11 / P1：后台分类术语直接暴露给玩家

**证据：** 首页分组标题包含“内容与运营”“工具 · 低优先级”；大量条目显示“可用”。

**改法：** 改为玩家任务语言：“新手必看”“常用工具”“更多资料”。正常能用不需要逐项“可用”标签；确有功能限制时，在对应入口旁短句说明“数据待更新”等真实限制。

**验收：** 首页不出现内部开发优先级、运营分类或无信息量的状态标签。

## 4. 图鉴承接页的问题：不修这些，首页再好看也会失效

### L01 / P0：筛选区域有真实布局缺陷，不是单纯“不够精致”

S3 的多行筛选有裁切、叠压；S4 和 M1 的定位、星级选项接近圆形，末尾还有不完整选项。顶部筛选、收集进度、命中数和独立排序卡共同占用了大量垂直空间。

源码将 `scroll-view` 本身设为 `.filter-row`，直接放多个 chip；相关样式缺少明确的行高度和内部内容布局约束。这是应优先排查的结构。没有做运行样式测量，不能断言只加一个 `height` 就能完全修复。

建议拆为：搜索 44px → 一行常用筛选/“更多筛选”44px → 结果与排序一行 → 内容。更多条件在底部面板中按“定位、星级、元素”等明确分组，带“重置”和“查看 N 个结果”。不要直接把三排筛选压缩到同一高度。

横向筛选若保留，应使用明确的滚动容器高度、内部横排内容层、禁止项目收缩，并给边缘留白和可继续滚动的提示。可见 chip 约 32–36px 高，整体可触区域达到约 44px；在 375px 宽时 44px 大约为 88rpx，不能把 64rpx 一概当成 44px。

验收：320/375/390/430px 宽度均无上下裁切、重叠、圆形变形；长标签能完整查看；筛选可撤销，已选条件可见，返回列表保留条件和滚动位置。最后两项本次尚未实测，列为回归要求。

### L02 / P0：头像有图不等于图片正确

M1 中佩佩、兰香子仍是攻略拼图。当前磁盘代码已指向 `hero_get` 获得立绘，但该图也不是理想的小头像：完整人物画幅缩到约 40px，脸部通常仍偏小。

应将头像、详情立绘、攻略长图拆为不同用途字段。角色头像优先 `Tex icon hero l …`，详情使用获得立绘，攻略海报只在攻略详情支持放大查看。不能用一个 `icon` 承担三个用途。

建议先检查全部 24 个 BWIKI 角色；不是只看两张加载成功就宣布通过。缺图时使用一致的首字/剪影加名字，不能让元素字替代全部身份信息，也不要伪造官方角色图。

验收：头像可认人、名称与人物对应、没有带小字的整张海报；图片失败不改变布局；网络恢复后支持合理重试。当前错误究竟来自旧项目、旧缓存还是远端资料，按第 1.2 节单独查明。

### L03 / P1：图鉴当前更像长摘要列表，缺少快速辨认效率

S3 在一个屏幕中能完整看到的奇波很少；每张卡主要是性格描述、来源、泛“战斗”标签和“详见 BWIKI”。头像只约 40px，无法承担识别任务。角色列表也优先展示长对白，而非可比较的关键字段。

推荐首页每类 4 张预览；分类页默认 3 列图片卡，供视觉浏览。需要比较栖息地、用途、技能时切到紧凑列表，记住用户选择。320px 屏幕可先验证 3 列文字是否足够，必要时降为 2 列，不强行保持列数。

图片卡固定显示名称和必要的元素/星级；详细说明进入详情。列表模式使用 56–64px 的头像、名称、两项可信属性、最多两行摘要；没有来源字段时不编造“家园生产”“可骑乘”等用途。

这不是要求照搬桌面八列。目标是让一屏可见对象增多，同时保留足够大的名称、图片和点击区域。

### L04 / P0：“收藏”被当作“已获得”，统计还会被筛选改变

角色、奇波页面的星标调用同一套 `favorites`，却把它展示为“已收集/已获得”。两页的 `favCount` 基于当前筛选后的 `list`，分母基于全量，筛选一改，所谓“总进度”也会变。

此外，`favorites.js` 设定所有分类共享 `MAX = 200`，超过后会截断旧记录；仅当前奇波就超过 200。这个机制不适合持久记录“全部已获得”。

近期最小改法：统一称“收藏”，删除大块收集进度；列表首部显示收藏筛选即可。若产品确实需要拥有记录，则另设“已获得”状态和持久化结构，不能继续与收藏混用；本次建议不先扩大这一功能。

验收：收藏和拥有只有明确的一种或各自独立；筛选不改变全局收藏数量；不会为了保存新收藏而无提示丢掉旧的“已获得”。星标有明确名称、约 44px 热区，点击不进入详情。

### L05 / P0：可信度标签表达错误，示例污染正式列表

奇波列表对每张卡无条件显示“待核实”，而 BWIKI 映射又把条目统一设为 `verified: true`。这是两个方向相反的表达。角色列表将示例并入正式条目，艾妮丝还存在同名重复。

“BWIKI 已收录”只证明来源存在，不代表技能、元素等每个字段已经由官方核实。应分别记录来源、适用版本和必要的字段缺失；默认列表剔除演示数据。字段确实缺失时用“暂缺”，不要让“未知/待核实/BWIKI收录”占据名称的同等视觉等级。

验收：正式数量排除示例和重复；页面不再无条件给全部奇波贴“待核实”；来源说明集中在页面说明或详情，重要例外才在单项提示。

### L06 / P1：列表状态与小操作仍有正确性缺口

源码中两页的“没有符合条件”空态没有 `v-if`，可能在有结果时也出现在页尾；首页输入框未监听 `clear`，而输入组件通过该事件要求父级清空值。图鉴的星标、输入清除按钮也未达到建议的可触面积。

验收：有结果时不出现无结果文案；无结果提供“重置筛选”；首页输入后点清除确实清空；返回详情前的查询状态可恢复。以上为静态发现和待执行用例，不冒充本次点击测试结果。

### 5.2 主视觉有两个可执行选择

**推荐：首页用经过确认可用、适合裁切的无字横图，配真实文本。** 左侧约 55% 放标题与按钮，右侧保留人物/奇波主体；正文区域用轻量单向遮罩，图片主体不统一降到低透明度。首轮没有合适图片时，宁可使用干净的事件文字卡，也不要放不相干的灵子缩略图。

**备选：完整展示已核验的公测海报。** 16:9、358px 宽时约 201px 高，比推荐的 144px 主视觉多占约 57px；必须相应把第二类预览后移。不要同时在图片和覆盖层重复两套日期大标题。海报自带文字需同时有可读文本摘要，不能只靠图片传达时间。

二者先选其一进行 390px 设计验收。不要把 16:9 海报用 `aspectFill` 硬裁成 2.5:1，再以“有图片了”验收。

### 5.3 图片的用途规范

| 图片位 | 建议展示方式 | 来源尺寸建议 | 不接受 |
| --- | --- | --- | --- |
| 首页主视觉 | 约 358×144px，明确焦点和文字安全区 | 对应裁切至少约 720×290，清晰源优先 | 120px 灵子缩略图放大、无关壁纸、文字被裁的整张海报 |
| 首页角色卡 | 每行 4 个，头像区约 76–80px，名字在下方 | 约 240px 级头像即可起步 | 全身立绘缩成小点、整张一图流 |
| 首页奇波卡 | 每行 4 个，方形图约 76–80px，完整主体 | 约 200–336px | 为铺满容器裁掉关键轮廓 |
| 分类页图片卡 | 默认 3 列，图片约 96–110px，按屏幕验证 | 约 240–336px | 名称覆盖在复杂脸部、过多角标 |
| 紧凑列表头像 | 56–64px 方形，独立于文字块 | 约 160–240px | 用全幅大海报靠缩小“适配” |
| 工具入口 | 同一套线性或轻填充图标，约 24–28px | 复用项目已有统一图标系统 | 同屏混合奖牌 emoji、盾牌 emoji、官方头像和随机卡牌 |
| 攻略封面 | 按文章选横图或对长图另做可读封面 | 按真实裁切导出 | 把长图整个缩小作为封面 |

建议素材记录包含：业务对象、用途、来源页面、原图尺寸、裁切焦点、适用活动期限、使用依据、替代文本。一个对象允许不同图片位使用不同图，不再只维护一个万能 `icon`。

已有 `wallpapers.json` 的 59 条记录只能视作候选集合，里面包含明确署名的插画；不能整体当成“官方可商用壁纸”。公开可访问、热链成功与可用于产品是不同问题。正式上线使用前确认对应素材的使用条件；不需要为本次只读评估申请下载授权。

AI 可用于独立设计的背景纹理、装饰和通用工具插图；不适合生成角色/奇波替身、真实地图或技能图标来填充图鉴。图鉴图片承担“这就是该对象”的识别职责。此前“重绘即可免版权/免授权”的表达也不应作为后续选材依据。

### 5.4 加载、失败与包体

首屏优先加载一个主视觉和当前可见缩略图，其余懒加载；所有图片预留比例，加载失败保留名称和同尺寸回退。首页主视觉也应有错误处理，当前模板未提供专门的失败回退。

设计预算建议：主视觉压缩后约 250KB 以内；首屏缩略图平均约 15KB 以内；首屏图片合计争取控制在约 450KB。它们是待测预算，不是已测性能。图片按展示尺寸提供变体，通过受控地址分发；不把几十张大图直接塞进主包，也不一次请求所有图鉴图片。

性能验收要记录真机型号、网络条件、冷启动/二次进入和图片可见时间；本次没有弱网和性能实测，不引用旧构建体积当成当前性能结论。

示意中的“19 天”为 2026-11-07 的日期示例，不应写死到界面。主视觉及卡片中的具体对象必须是已核对的真实内容；无浏览记录时不要伪造“最近浏览”，没有热度数据时不要标“热门”。

默认角色和奇波各选 4 个资料较完整、图片清晰的对象，作为固定“速查”预览；以后可用真实最近浏览替代，但不同时堆叠多个推荐模块。

### 6.2 390×844 的纵向预算

以下是逻辑像素的布局目标，不能用附件缩放后的像素直接当 CSS 尺寸。状态栏、微信导航和安全区随设备变化，需分别验证。

| 模块 | 高度预算 | 累计内容高度约值 |
| --- | ---: | ---: |
| 顶部留白、搜索、下间距 | 12 + 44 + 12 | 68 |
| 主视觉及下间距 | 144 + 16 | 228 |
| 固定八入口及下间距 | 116 + 20 | 364 |
| 角色标题、间距、图片卡、下间距 | 24 + 8 + 116 + 20 | 532 |
| 奇波标题、间距、图片卡 | 24 + 8 + 104 | 668 |

状态栏和导航按约 88px 估算，底部安全区按约 34px 估算，剩余内容约 722px。因此推荐方案具备把两类预览放入这一目标屏幕的空间可能性；这不是已渲染效果保证。小屏优先保住搜索、快捷入口和第一类预览，第二类自然滚动，不靠缩到 10px 字号强行塞入。

### 6.3 视觉规范

| 项目 | 建议起点 | 目的 |
| --- | --- | --- |
| 背景 | 低饱和冷灰蓝，接近现有 `#f3f5fb` | 保留统一基调，减少大面积装饰 |
| 主行为色 | 复用 `#2f6bff`，深色单独校验 | 行为含义一致 |
| 主标题 | 18px / 600；主视觉标题约 20–22px | 标题与功能名称有明确层级 |
| 名称、正文 | 14–16px；正文行高约 1.5 | 名称能读、摘要能扫 |
| 说明文字 | 12–13px，足够对比 | 通过减字降低负担 |
| 页面边距 | 16px，模块内边距 12–16px | 建立统一对齐线 |
| 间距 | 4 / 8 / 12 / 16 / 24px | 控制节奏，减少随意数值 |
| 圆角 | 内容卡约 12px；小图约 8px；胶囊留给筛选 | 不让所有对象都像按钮 |
| 阴影 | 静态内容尽量无阴影，必要浮层才强调 | 降低白盒子堆叠感 |
| 动效 | 按压反馈约 100–160ms，轻量明暗或位移 | 确认点击，不靠持续运动吸引注意 |

深色专项：首页 `.verinfo__name` 固定 `#333`，版本标题和摘要也有硬编码色。若卡片底为现有深色 `#1c2233`，`#333` 对比仅约 1.25:1。此为源码色值组合风险，本次未运行深色首页。后续应使用语义色并实拍，不再凭“根节点有 theme-dark”判定通过。

### 6.4 交互细节

1. 首页搜索确认后进入全局结果；有文字时清除按钮有效。返回首页保留或清空的策略保持一致，不出现框里有词但结果不对应。
2. 角色/奇波预览整张卡点击进对应详情；“查看全部”进该分类，不把两种目标藏在同一个小箭头中。
3. 主要按钮和图标操作按约 44×44px 热区设计，布局不必把所有图标视觉尺寸也放大到 44px。
4. 首页默认无自动轮播；内容有效期到达后撤下事件，不能只换倒计时数字。
5. 图鉴筛选打开面板后显示当前条件；确认、重置、关闭各有明确结果；关闭不应意外清掉已选条件。
6. 收藏后立即更新星标并给简短反馈；返回列表时状态一致。若维持收藏语义，不显示“你已获得”。
7. 一级入口较多不等于必须新增底部导航。首轮通过固定入口和目录完成结构收敛；底部导航会涉及路由、返回和状态管理，另有明确需求时再评估。

## 9. 对此前结论的修正

| 旧式结论或做法 | 本次修正 |
| --- | --- |
| 有宫格、有收藏、有图，就与参考站等效 | 要看入口可发现性、图片是否正确、状态语义是否成立、用户能否完成任务 |
| 已做主题变量，深色就算通过 | 首页仍有固定 `#333` 等色值，需要运行截图和对比度检查 |
| 图多、条目多，首页更有价值 | 首页价值来自快速找到真实资料；来源混杂、重复和示例会削弱信任 |
| 任意灵子图加遮罩就能成为高级游戏视觉 | 需要内容相符、主体清晰、裁切合理的图片；遮罩不能修复选图错误 |
| 一图流海报可以当角色头像 | 图像用途错误，头像应使用专用人物图片 |
| 订阅开关能保存，等同提醒能力可用 | 必须明确真正能否发送；本地偏好不应包装成已预约提醒 |
| 自绘大陆配真实坐标，地图体验就等效 | 找点依赖地形、坐标对齐与可识别地标；未经验证不升为核心首页工具 |
| 多页渲染成功、自动化无报错，体验就优秀 | 本次运行仍可见错误图片和筛选形变，说明旧验收不足 |
| 重绘或 AI 生成即可解决所有图鉴缺图 | 通用装饰可以设计，图鉴对象需要准确身份，不能用想象图补真资料 |

下一轮应交付的是“可信资料 + 正确图片 + 清楚的首页 + 可用的筛选”，而不是新的页面数量、更多装饰图或一份没有实际证据的高分报告。
