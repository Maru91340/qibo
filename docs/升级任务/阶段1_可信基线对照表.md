## 1. 本轮结论：方案 1.2「评的是哪个版本」已查明

方案 1.2 记录 S2 首页截图为「奇波 212 / 角色 30 / 官方图 — / 图鉴条目 1313」，与磁盘源码（215 / 32）对不上，原因未定。本轮在微信开发者工具模拟器 storage 持久化文件中找到运行侧缓存，按首页 `stat` 公式重算得到 **212 / 30 / 0 / 1313**，与 S2 逐位一致。

结论：S2 评的是 **2026-11-05 的一次旧云端缓存快照**（`revision = 7badbdda51e74511`），不是磁盘当前的 `catalogs.json` / 内置子集 / 云端 seed，也不是「图片请求失败」。差异根因是缓存版本键与资料版本共用同一字符串、未随内容更新，导致旧缓存一直压制新数据。

## 5. 差异根因链（本轮新增结论）

1. `content.js:26` 以 `qbxzs:cache-bv !== CATALOG_VERSION` 判断是否 `clearCatalogCache()`；
2. `catalog.js:10` 的 `CATALOG_VERSION` 只由 `generated.generatedAt` 拼成，源码全量 / 内置子集 / 云端 seed 三处均为 `2026-11-05T00:47:46.864Z`；
3. 运行侧 `qbxzs:cache-bv` 也是同一字符串 → **清缓存条件不成立**；
4. `getCatalog()` 的 `entry(type)` 命中旧的 17 类云端缓存 → `source = 'cloud'`，优先返回缓存 `content`，绕过 `bundledCatalog`；
5. 旧缓存 12 类条目无 `icon` → `stat.images = 0` → 首页「官方图 —」；
6. 缓存 `fetchedAt`（2026-11-05 17:14Z / 09:38Z）早于 seed `publishedAt`（2026-11-05 19:11Z），且各类 `revision` 与 seed 的 `catalog.types` 不同（仅 `affix` 相同）→ 云端已有新快照但未在运行侧生效；
7. 为何 `prefetchCatalog()` 未增量替换（云函数是否部署、manifest 是否返回 `notModified`、云端 ENV_ID 是否配置）**未能验证**，需云开发控制台与运行日志（关联待确认 #2 / #20）。

> 方案 1.2「图片或文案修复若不变更 `CATALOG_VERSION`，不能指望缓存自动淘汰旧数据」的判断，本轮从运行侧持久化数据得到直接印证。**这是阶段 2 的前置风险**：在缓存机制或版本标识处理前，改磁盘数据/图片不会自动反映到运行界面。
